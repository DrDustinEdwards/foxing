## Threat model

Foxing is a reading app ("Letterboxd for books") at `foxing.app`. The Worker serves the React Router app and `/api/v1`. A second Worker, `foxing-admin-mcp`, is a wrapper over `/api/v1/admin`. Its own description says it contains no policy. It holds no Stripe key, no D1, and no R2. It has a service binding to the app Worker.

Callers:

- Anonymous visitors on marketing pages, the catalog, public journals, and `GET /health`.
- A reader signed in with Better Auth (email or Google).
- Stripe, on the webhook, after signature verification, once the four billing secrets exist.
- Cron (push sweep `*/5`, backup `17 3 * * *`, companion cache `0 8 * * *`).
- An admin, by cookie session or by the admin MCP. The MCP path is an operator bearer plus `X-Foxing-Admin-Id`, then the same `requireAdmin` check.
- The Supabase edge function `ai-companion` on project `ekjpsuewrkvqzbuteurc`, which the mobile client no longer reaches.

Trust changes at: the Better Auth session, `requireAdmin` on `profiles.is_admin`, the operator token compare, Stripe signature verification, the backup exclude list, and the MCP audience plus `ADMIN_EMAIL` check that runs before the MCP SDK. Private clubs and private profiles are supposed to change trust and, on the API, mostly do not (FX-1, FX-2). Google OAuth tokens sit in D1 as plaintext (FX-3).

STRIDE, short: spoofing is the session and the operator token; tampering is a club post, a diary row, or a subscription tier; repudiation is the admin audit log; information disclosure is a private club, a private profile, and OAuth tokens at rest; denial of service is the public catalog and the ungated edge-function cache; elevation is a private-club join, an operator token, or a push to unprotected `main`.

## Findings

### FX-1 CRITICAL, area 1, confidence confirmed

`GET /clubs/:id` (`packages/api/src/routes/clubs.ts` lines 62-72) hides a private club unless `membership.status === "active"`. These sibling reads do not load the club and do not check visibility or membership:

- `GET /clubs/:id/members` (lines 75-78). `listMembers` (`packages/core/src/repositories/clubs.ts` lines 219-224) selects the full `club_members` row, including `userId`, `status`, `role`, `banReason`, `bannedBy`, `mutedUntil`, and `mutedBy`.
- `GET /clubs/:id/threads` (lines 80-82).
- `GET /threads/:id` (lines 85-91) returns the thread and `listPosts`, which returns post content.
- `GET /clubs/:id/polls` (lines 93-106) returns polls, tallies, and `voteCount`. The raw ballots stay on the server. Vote user ids are not in the JSON.
- `GET /clubs/:id/meetings` and `GET /clubs/:id/schedule` (lines 109-117).

`POST /clubs/:id/join` (lines 169-172) calls `joinClub` (`packages/core/src/domain/clubs.ts` lines 125-160). `joinClub` never checks `visibility` or the join code. `memberApproval` defaults to false (`packages/core/src/schema/clubs.ts` line 33). `resolveJoinStatus` (`packages/core/src/domain/membership.ts` lines 24-30) returns `"active"` when approval is off and the club is under its cap. A private club at the defaults lets any signed-in caller who knows the id become an active member.

The id does not have to be guessed. A join or an approval emits `joined_club` with `targetId: clubId` and `visibility: "public"` hardcoded (`packages/core/src/events/emitter.ts` lines 88-92 and 109-112). `GET /api/v1/feed` (`packages/api/src/routes/social.ts` lines 120-126) returns those event objects, including `targetId`, to followers of the actor (`packages/core/src/domain/social.ts` lines 42-50 and 184-216). A follower then calls the member and thread routes with no further check. Anonymous GET works once the id is known.

The web loaders do the check the API skips (`apps/web/app/lib/clubs.server.ts` lines 32-34 and 78-80). The web feed drops `targetId` (`apps/web/app/lib/social.server.ts` lines 59-71). The API does not. Search hiding is tested (`menus.integration.test.ts` passed). Private-club child routes and `joinClub` are not. Removing the detail check left `clubs.integration.test.ts` green.

Ids are nanoid. WebSocket connect (clubs route around lines 367-374) does check membership, then sets `uid` on the Durable Object URL. `ClubRoom` trusts that query param. The only caller is the binding. Writes go through moderator checks. Those paths are not this finding.

Smallest fix: one helper that loads the club and applies the same private-membership rule, used by every child read and by `joinClub`. Invite-code join stays on `joinByCode`. Stop publishing a private club id on an activity row whose visibility is `"public"`.

### FX-2 MAJOR, area 1 and 3, confidence confirmed

`GET /u/:username` (`packages/api/src/routes/profiles.ts` lines 79-83) loads `getProfileByUsername` with no visibility predicate and returns `toPublicProfile` (lines 196-206 of `packages/core/src/repositories/profiles.ts`): username, display name, avatar, backdrop, bio, favorite genres, created at. The type comment on line 19 says the projection honors the owner's visibility later. The route comment says the route is visibility-aware.

Search honors it (`coalesce(json_extract(... visibility.profile), 'public') = 'public'`). Public recap checks it (`social.ts` lines 140-148). The web loader returns a branded notice with username, display name, and avatar only (`apps/web/app/lib/social.server.ts` lines 91-104). `menus.integration.test.ts` "finds public people by name and hides private profiles" passed.

A normal unauthenticated `GET /api/v1/u/:username` returns the bio of a private profile. The username is already in the URL.

Smallest fix: when `visibility.profile` is not public and the viewer is not the owner, return the same minimal identity, or 404.

### FX-3 MAJOR, area 3, confidence confirmed

The `account` table (`packages/core/src/schema/auth.ts` lines 31-47) stores `accessToken`, `refreshToken`, and `idToken` as text. `getAuth` (`apps/web/app/lib/auth.server.ts` lines 34-67) configures Google and does not set `encryptOAuthTokens`. Better Auth stores the password column as a hash. The OAuth tokens are stored as given.

The backup exclude list omits `account`, so a restore does not revive those tokens. The live D1 row still holds a Google refresh token. Nothing in the API selects those columns. Admin user detail does not select them (`packages/core/src/repositories/admin.ts` lines 169-185).

Smallest fix: set `encryptOAuthTokens` with a key from a Worker secret, and rotate the Google tokens already stored.

### FX-4 MAJOR, area 4 and 5, confidence confirmed

`deleteAccount` (`packages/core/src/domain/account.ts` lines 221-232) walks `REGISTRY`. Line 155 is `byColumn("clubs", clubs, clubs.creatorId)`, so every club that user created is deleted. Club member posts cascade with the club.

`deleteClub` (`packages/core/src/domain/clubs.ts` lines 111-114) still calls the account-deletion policy for authored club content an open decision and says not to resolve it there. `deleteAccount` already deletes those clubs. A reader deleting their own account destroys other members' club. Backups hold old rows for the d1-dump retention (14 days, 8 ISO weeks, 6 months). The deletes are sequential, not one transaction, so a failure in the middle leaves a partial erasure.

Rows that can survive when foreign keys are off: `close_friends` where the deleted user is `friend_id` (the registry deletes the `user_id` side; the schema declares `ON DELETE CASCADE` on both columns), `reports` where they are `target_id` (no user foreign key), other users' notifications, and `admin_audit_log` (plain text actor, not a foreign key).

Journal posts that survive with `author_id` null are intentional. They are listed in `ACCOUNT_EXPORT_EXCLUDED` (lines 200-209) as public content. Diary entries are in the registry (line 157). Export and delete use the session id only (`packages/api/src/routes/account.ts` lines 13-32). The completeness test passed.

Smallest fix: transfer or detach clubs on account delete until that open decision is made. Wrap the erasure in one batch.

### FX-5 MAJOR, area 1 and 2, confidence confirmed in code, gateway flag suspected

`apps/mobile/supabase/functions/ai-companion/index.ts` `getUserIdFromAuth` (lines 240-259) base64url-decodes the JWT payload and returns `sub`. It does not verify the signature. The comment says the Edge Functions runtime already verified it via `verify_jwt: true`. No `config.toml` in the repo sets that flag. `apps/mobile/lib/claude.ts` repeats the same comment.

`deleteAccount` (lines 837-857) requires `viewerId` from that decode, requires `payload.userId === viewerId`, then calls `admin.auth.admin.deleteUser(viewerId)` with `SUPABASE_SERVICE_ROLE_KEY`. That deletes the Supabase auth user. It does not delete the D1 account. CORS `Allow-Origin` is `*`.

`PLUS_REQUIRED_ACTIONS` (lines 32-48) does not include `chapter_summary`, the catalog generators, or `delete_account`. Cache hits for catalog actions return before `enforceLimitsAndGate` (lines 973-991). The Plus check reads Supabase `profiles.subscription_tier`, which is not in `apps/mobile/supabase/migrations/001_initial_schema.sql`. A missing column is treated as free.

The shipped mobile client cannot call this. `apps/mobile/lib/supabase.ts` is a throwing proxy, and `apps/mobile/lib/claude.ts` still calls `supabase.functions.invoke('ai-companion')`.

The function URL is live. `GET https://ekjpsuewrkvqzbuteurc.supabase.co/functions/v1/ai-companion` returned HTTP 401, `sb-error-code` `UNAUTHORIZED_NO_AUTH_HEADER`, `sb-gateway-version` 1, served by `supabase-edge-runtime`. The function's own non-POST path would be 405, so this 401 happened before the function body. A headerless request is refused by the gateway today. A forged token was not sent.

Smallest fix: verify the JWT inside the function, or fail closed, and pin `verify_jwt` in config. Or remove the function if mobile no longer calls it. See FX-17 for the ungated catalog actions.

### FX-14 MINOR, area 1, confidence confirmed

Role changes (suspend, tier, admin) are preview-then-perform (`admin-confirm.ts`). The confirm token matches `/^[0-9a-f]{64}$/`, lives 120 seconds in `APP_KV`, and is deleted before the write. `DELETE /admin/users/:id` (`packages/api/src/routes/admin.ts` lines 300-306) calls `deleteAccount` on the first request after `requireAdmin` and a self-delete block. ### FX-15 MINOR, area 1 and 2, confidence confirmed

`operator.ts` compares `Authorization: Bearer` to `ADMIN_OPERATOR_TOKEN` with `safeEqual`. A missing env token is 401. A wrong token is 401. `X-Foxing-Admin-Id` is required. `getOperatorActor` returns any user `{id, email}`, not `is_admin`. `requireAdmin` then re-reads `profiles.is_admin` and refuses a suspended profile. The plant that skipped `isAdmin` made a non-admin operator call return 200, so the second check is what holds. A leaked operator token plus any admin user's id is full admin, and the audit row records that id. The token is the secret. Every admin handler calls `requireAdmin`. Smallest fix: keep the token in a Worker secret and alert on operator audit rows.

### FX-16 MINOR, area 2 and 12, confidence confirmed

`apiHandler` (`mcp/src/api-handler.ts` lines 44-71) runs after the OAuth provider validates the token. It checks audience, `isAdminUser` against `ADMIN_EMAIL` (fail closed when unset), and 30 requests per 60 seconds per email, then `handleMcp`. When `auth.scope` is not an array it defaults to `[foxing.read]` (line 70). A write still requires `foxing.write`. Smallest fix: refuse when scope is missing.

`@modelcontextprotocol/server` 2.0.0 is inside `>=2.0.0 <2.3.0` (shared HTTP transport, memory use during validation, and a moderate audience advisory). `npm audit` in `mcp/` reported those highs. `apiHandler` authenticates the admin before `createMcpHandler`, and the handler builds a new server per request (`mcp/src/mcp-handler.ts` lines 32-61). This is not an anonymous exploit. The memory cap is still the SDK default, and only an admin token reaches it. `agents` 0.24.0 pulls client and SDK highs. Foxing does not construct an outbound MCP client in `src`. Smallest fix: upgrade `@modelcontextprotocol/server` past 2.3.0 and `agents` past the affected range.

`foxing_set_book_of_month` uses `SCOPE_READ` for list and get and `SCOPE_WRITE` otherwise, while the tool-level annotations are `destructive: true` and `idempotent: false` for every action, including list and get. Smallest fix: set annotations from the action.
